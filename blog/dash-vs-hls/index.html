DASH 与 HLS 怎么选？流媒体协议全方位对比 DASH vs HLS: How to Choose a Streaming Protocol

2026-08-28 · 6 min read

一、它们其实是一类东西

DASH（MPEG-DASH）和 HLS（HTTP Live Streaming）都采用同一套底层思路：把视频切成许多小分片，再用一个文本清单描述这些分片，播放器按网络状况挑合适的清晰度。这套“清单 + 分片 + 自适应”模型，让视频能像普通网页一样走 HTTP、享受 CDN 缓存，也方便穿越防火墙。

二者最大的区别不在原理，而在阵营与文件格式：HLS 是 Apple 主推、事实标准；DASH 是 MPEG 国际标准，标签更中立。下面从几个维度拆解。

二、文件格式对照

  • 清单文件：HLS 用 .m3u8（基于 M3U 文本）；DASH 用 .mpd（基于 XML）。
  • 分片封装：HLS 传统用 .ts，新规范也支持 .fmp4；DASH 多用 .m4s（ fragmented MP4）。
  • 加密：两者都支持 AES-128 / DRM，HLS 用 EXT-X-KEY，DASH 用 Common Encryption（CENC）。

三、兼容性与“浏览器原生支持”

这是最容易踩坑的一点：

  • Safari（含 iOS/macOS） 原生支持 HLS，可以直接用 <video src="x.m3u8"> 播放；对 DASH 没有原生支持。
  • Chrome / Firefox / Android 原生支持 DASH（通过 MSE），但对 HLS 原生支持有限，通常需要借助 hls.js 这类库。
  • 所以“到底谁更兼容”取决于你的目标平台——苹果生态偏 HLS，开放浏览器偏 DASH。

四、延迟与实时性

传统 HLS / DASH 都是“切片后播”，端到端延迟通常在 10~30 秒，适合点播和常规直播。若要秒级低延迟（LL-HLS / LL-DASH）需要额外配置，且并非所有播放器都支持。如果你的场景是“主播实时互动”，两者都不是最优选，但常规直播两者都能扛。

五、国内可用性

在国内，CDN 厂商对两种协议都支持良好，文件走 HTTPS 时 CORS 是绕不过去的一环——任一协议只要分片域名和页面域名不一致，都必须正确配置 Access-Control-Allow-Origin。这也正是很多“播不了”的真正原因。

六、到底选哪个

  • 面向苹果用户为主 / 想用原生播放省事 → 优先 HLS（.m3u8）。
  • 面向全平台 / 国际标准 / 大厂生态（如 YouTube 系） → DASH（.mpd）更常见。
  • 最稳的做法：同时产出两套，让播放器按设备挑——本站播放器就同时内置 hls.js 与 dash.js，粘贴任一格式都能直接播。

1. They are essentially the same idea

DASH (MPEG-DASH) and HLS (HTTP Live Streaming) share the same core design: chop video into small segments and describe them with a text manifest, letting the player pick the right quality by network conditions. This "manifest + segments + adaptive" model lets video travel over plain HTTP, benefit from CDN caching, and pass through firewalls easily.

The real difference is not the principle but the camp and file format: HLS is Apple-backed (de-facto), while DASH is an open MPEG standard. Let's break it down.

2. File format comparison

  • Manifest: HLS uses .m3u8 (text-based M3U); DASH uses .mpd (XML).
  • Segment container: HLS traditionally uses .ts, newer spec also supports .fmp4; DASH mostly uses .m4s (fragmented MP4).
  • Encryption: both support AES-128 / DRM; HLS uses EXT-X-KEY, DASH uses Common Encryption (CENC).

3. Compatibility and "native support"

  • Safari (including iOS/macOS) plays HLS natively via <video src="x.m3u8">, but does not natively support DASH.
  • Chrome / Firefox / Android support DASH natively (via MSE) but need a library like hls.js for HLS.
  • So "which is more compatible" depends on your target platform — Apple-leaning for HLS, open-browser-leaning for DASH.

4. Latency and real-time

Traditional HLS / DASH slice-then-play, with end-to-end latency usually 10–30s, good for VOD and normal live. Sub-second low latency (LL-HLS / LL-DASH) needs extra config and player support. For interactive streaming, neither is ideal, but both handle normal live fine.

5. Availability in China

Domestic CDNs support both protocols well. The one unavoidable pain is CORS: whichever protocol you use, if the segment domain differs from the page domain, Access-Control-Allow-Origin must be set correctly — that's the real reason many streams "won't play".

6. Which to choose

  • Mostly Apple users / want native playback → prefer HLS (.m3u8).
  • Cross-platform / international / big-ecosystem (e.g. YouTube) → DASH (.mpd) is more common.
  • Safest: produce both and let the player pick by device — this site's player bundles both hls.js and dash.js so any format plays.
